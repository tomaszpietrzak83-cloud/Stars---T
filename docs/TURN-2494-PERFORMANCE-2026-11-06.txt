Concrete next optimization candidates; NOT implemented in this audit
1. Target ranking is recomputed per friendly fleet. sortedPatrolTargets already
   caches each enemy within one sort, but the next fleet repeats the work.
   patrolTargetPriority calls patrolColonyDeadline, then rank calls it again.
   That helper scans PlanetIntels and can call patrolDefendedColony, which calls
   enemyApproachingColony and scans planets again. Reuse one computed deadline
   and static threat rank per enemy/report snapshot; retain per-fleet distance
   and exact stable ordering/ties. A player-owned-colony index would avoid
   scanning all 2744 planet reports for every ownership/direction check.
   Locations: cs/patrolsort.go:10, :25, :78; cs/patrolqueue.go:16;
   cs/patrolautomation.go:808; cs/scoutrecon.go:98.
2. Routing and return fuel still evaluate many dock/warp alternatives and
   geometric threat intersections. Profile these nested loops before extending
   caching; existing corridor results are scoped to one route search. Any reuse
   must include fuel/cargo/engine, report and policy changes; geometric filtering
   must preserve threat boundaries, civilian stops, gates and return reserves.
   Locations: cs/automaticroute.go:153, :193; cs/logisticsautomation.go:253.
3. GC takes substantial CPU. Avoid repeated temporary rank maps, cloned enemy
   lists and route arrays where lifetime/ownership allows. A scoped allocation
   profile is needed before attributing the allocation volume to a particular
   function; a CPU profile alone does not provide allocation-byte counts.
AI parallelism and database tuning are lower priorities on this particular save.
No speculative percentage speedup is promised for these unimplemented candidates.
